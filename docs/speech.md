# Speech pipeline

Flow: device button (single press) -> `audio.start_capture` -> PCM frames -> end-of-speech (energy VAD) or second press -> STT -> onboarding answer *or* responder -> sentence split -> TTS (next sentence synthesized while the current one plays) -> `audio.play`. Host loop calls `VoicePipeline.poll()`; STT, reply and TTS run on worker threads, so a press can always cancel (TRANSCRIBING/THINKING) or interrupt (SPEAKING, which stops the speaker).
Animations follow the behavior engine (listening -> thinking -> talking -> idle). Looping animations outrank idle, so the pipeline sends `animation.stop` before returning to idle (a missing stop left the device stuck in "talking" during testing).

## Rules (tested)
- Microphone opens only on a single press of the configured button; double/long presses never start listening. The device can refuse (muted, low battery): the pipeline then speaks a scripted line and never tries to change the device's mic setting.
- Silence, clicks and empty transcripts never reach STT/LLM/memory. Transcripts are cleaned (control characters, length) because they are untrusted text.
- Audio is dropped as soon as STT has it; no transcript or audio is kept or logged here (`log` holds stage names only). Whatever consumes transcripts (responder, memory) owns its own retention rules.
- STT/LLM/TTS failures and timeouts are spoken from scripted lines (`species/*/speech.yaml`), never from model output or exception text. Bad TTS audio (empty, odd length, > 30 s) is rejected. Style is checked against the protocol's voice styles.
- Device sleeping or unresponsive: the pipeline stands down to IDLE instead of talking into the void. Corrupt capture (sequence gap) is not transcribed.
- Host-initiated speech (`speak()`, `offer_onboarding()`) never opens the microphone.
## Engines
`companion/speech/engines.py`, local only, no network at run time.
- STT: `WhisperRecognizer` (faster-whisper, `pip install -e .[stt]`). Model must already be on disk (`python -m tools.fetch_models whisper --size small.en --out models/whisper-small.en`, one-time, needs internet); `local_files_only=True`. Guards: clips < 0.2 s or RMS < 120 return "" without calling the model; no-speech segments dropped; known silence hallucinations ("Thank you.") dropped on clips < 2 s.
- Measured 2026-10 on the owner's laptop (Ryzen 5 3500U, 5.7 GB RAM, Linux): `small.en` was accurate but too slow (RTF 0.75 to 1.2) and once looped for 24 s printing "Ahhhh..." on noisy input; `base.en` ran at RTF 0.2 with 324 MB and heard a live microphone phrase correctly with a TV on, but mis-heard an unusual machine-spoken sentence. Default is `base.en`. Her voice is untested. The engine now stops decoding runaway loops (`max_new_tokens` tied to audio length) and throws away degenerate output ("Ahhhh...", repeated words, impossible words per second).
- TTS, natural voice: `KokoroSynthesizer` (Kokoro-82M via `kokoro-onnx`, Apache-2.0 weights; female voices `af_heart` (default), `af_sarah`, `af_bella`, `af_nicole`, `af_sky`, `af_nova`, UK `bf_emma`). Run for real in the sandbox: it works and is the most natural CPU voice in the 2026 comparisons I found (secondary sources, unverified by me by ear: I cannot listen). Measured: the full 325 MB model runs at RTF 0.35 to 0.5 on a 4-core CPU; the 92 MB int8 file was FIVE times slower (RTF 2.0) there, so `fetch_models kokoro` downloads the full one (checksum pinned). Style only changes speed, not pitch or emotion. Not ChatGPT-voice level; ElevenLabs-class cloud voices are out because nothing may leave the home network. Not yet verified on the owner's machines. Its phonemizer loads espeak-ng (GPLv3) as a library: fine for a personal gift, check before selling.
- TTS, robotic fallback: `EspeakSynthesizer` (espeak-ng subprocess, text on stdin, WAV parsed and resampled to 16 kHz). Styles map to pitch/speed/volume (hand-guessed). Clearly robotic. espeak-ng is GPLv3 (separate process); Piper (also GPL) or another voice can replace it behind `SpeechSynthesizer`.
- Checked 2026-10 in this sandbox: espeak-ng ran for real (valid speech audio, played through the voice pipeline and the simulated speaker, tests green). faster-whisper could NOT be run for real here (model hosting is blocked by the sandbox proxy), so the Whisper adapter is tested only with a stub model: recognition accuracy, speed on the MiniForum and the hallucination filter on real audio are UNVERIFIED. PocketSphinx was tried as a stand-in and misheard clean synthetic speech, so it was not adopted.
## End-of-speech detection
The energy detector learns the room: the quietest 10% of windows approximate noise and speech must be 3x louder (capped), once something clearly louder than the noise has been heard. Before this, a fixed 500 threshold meant a hot laptop mic (RMS ~18000) never produced "silence", so she kept listening until the 15 s limit and seemed not to answer. Still untested on the real device microphone.

## Paced speech (silence)
Scripted exercise text may contain `[pause N]` (seconds) and a reply may carry trailing `pauses`; both only count when `Reply.paced` is True, which only the psychology path sets. Anywhere else (model replies, transcripts, device lines) the markers are stripped, so nothing but a reviewed script can make her go quiet. Silence is played through the same paced playback as speech (10 s clips, each pause <= 60 s, <= 120 s total), never touches the synthesizer, and a button press interrupts it like speech. Slow breathing now speaks "in for four ... out for six" with real gaps. Before this, the exercise's `wait_s` was computed but dropped, so the guide was spoken in one breath. Timings are untested with a real person; the 4/6 counts include speech time and may need tuning.
## Limits
VAD threshold (500 RMS) and 1.0 s trailing silence are guesses until tested on the real microphone; no echo cancellation (the speaker can leak into the mic if the user presses during speech), no wake word, no streaming partial transcripts, STT/TTS threads cannot be killed (a hung engine is abandoned, not stopped). Fakes produce tones and scripted text, so audio quality and recognition accuracy are untested.
